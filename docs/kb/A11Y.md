# Accessibility knowledge base (UNIX Salla theme)

Course notes for `unix-a11y-auditor` and anyone who builds UI. Target: **WCAG 2.2 AA**, Arabic (RTL) first, English (LTR) second. These notes come from primary sources: W3C WCAG 2.2 Understanding docs, the WAI-ARIA Authoring Practices Guide (APG), web.dev *Learn Accessibility*, MDN and W3C Internationalization. Researched 2026-11-09.

How to read a rule: **Rule** · *SC* · **Test** · Source.
- `grep` lines run from the repo root.
- "VO" means VoiceOver. "Kbd" means keyboard only, no mouse.
- **UNVERIFIED** marks points the sources don't state outright: our inference, or behaviour that has to be checked on a device.
- Where the project wants more than AA (44px targets, for example), the AA floor is given as well, so the auditor can grade findings by severity.

Project context:
- Twig views are in `src/views`. SCSS uses logical properties only, in `src/assets/styles`. JS is vanilla, in `src/assets/js`.
- `salla-*` web components render in shadow DOM. Problems inside the shadow DOM are reported as "Salla-side", with a workaround.
- Shared drawer logic is in `src/assets/js/partials/unix-drawer.js`: `.app-inner` becomes inert, Tab is trapped, Esc closes, focus returns to the trigger.
- The global focus ring is `.theme-unix :focus-visible` in `src/assets/styles/01-settings/unix-tokens.scss:360`.

## 1. The six new 2.2 criteria (AA and A), in practice

**2.4.11 Focus Not Obscured (Minimum), AA.** When a component gets keyboard focus, author-created content must not hide it *entirely*. Partial overlap passes.
- Sticky headers and footers that fully cover the focused item fail (failure F110).
- A modal that takes focus passes.
- Persistent non-modal content (a chat widget, a cookie bar) fails if it fully covers focus. It is acceptable if the user can reveal the item without going back to dismiss it (Esc, scrolling).
- Sufficient technique C43: CSS `scroll-padding`.
- **Test:** Kbd, Tab *and* Shift+Tab through the whole PDP and PLP at 375px and 1280px. Watch every focused item that passes under the fixed header (`unix-header.scss:20,80`) and the mobile sticky ATC (`unix-sticky-atc.scss:7`).
- **grep:** `grep -rn "scroll-padding-block\|scroll-padding-top" src/assets/styles`. Today it returns nothing for `html`, so a manual check is required.
- Fix pattern: `html { scroll-padding-block: var(--header-h) var(--sticky-atc-h); }` (logical property).
- Source: focus-not-obscured-minimum.html

**2.5.7 Dragging Movements, AA.** Anything done by dragging must also work with a single pointer and no drag.
- In scope: carousels where the content handles the drag, and range sliders (price filter). The fix is prev/next buttons, clicking the track, or number inputs.
- Out of scope: native CSS `overflow` scrolling and user-agent scrolling.
- Swipe gestures where the element doesn't follow the finger fall under 2.5.1 Pointer Gestures. Those need a button too.
- **Test:** Using only taps or clicks, reach every slide of the gallery, product carousels and collections grid, and set every filter value.
- **grep:** `grep -rn "pointerdown\|touchstart\|touchmove" src/assets/js`. Every hit needs a button alternative.
- Source: dragging-movements.html

**2.5.8 Target Size (Minimum), AA.** A pointer target must be at least 24×24 CSS px. The test: an axis-aligned 24px square fits inside the target. Exceptions:
1. **Spacing.** A 24px-diameter circle centred on each undersized target doesn't intersect another target or another such circle. For example, 20×20 targets with a 4px gap pass.
2. **Equivalent.** Another control on the page does the same thing and meets the size.
3. **Inline.** The target sits in a sentence, or line-height limits it.
4. **User agent.** The browser sets the size and the author hasn't changed it.
5. **Essential.**

Project standard: 44px, as in DS. The documented exception is the 40px announcement link (D10). That still passes AA, so don't re-flag it.
- **Test:** DevTools, select each icon button (heart, close, qty ±, swatch, carousel arrow, pause), read its computed box. Measure the spacing circles for swatch rows.
- Source: target-size-minimum.html

**3.2.6 Consistent Help, A.** If help (contact details, a contact form, a FAQ or self-help page, a chatbot) repeats across pages, it must come in the same *relative serialized order* on every page.
- It doesn't require help to exist, and it doesn't require the same visual spot. Comparisons are made within one layout variation (mobile vs desktop can differ).
- For us: the footer contact/WhatsApp links and any floating WhatsApp or chat app must keep the same DOM order on every template, including `layouts/customer.twig`.
- **Test:** Compare where the help links fall in DOM order (`document.querySelectorAll('footer a')`) on home, PDP, cart and account.
- Source: consistent-help.html

**3.3.7 Redundant Entry, A.** Information the user already gave in the *same process* is auto-filled or offered for selection. Browser autofill alone doesn't count. Exceptions: essential, security (confirming a new password), data no longer valid.
- Checkout is Salla-hosted (Salla-side). Theme scope: the Size Finder answers (height and weight) shouldn't be asked again inside one session or flow, and the delivery-estimate city shouldn't be retyped. **UNVERIFIED** whether a cross-page flow counts as "the same process" here.
- Source: redundant-entry.html

**3.3.8 Accessible Authentication (Minimum), AA.** No cognitive function test (remembering a password, transcribing a code, a puzzle) at any step unless:
- an alternative method exists,
- a mechanism helps (paste, password manager, autofill),
- it is object recognition, or
- it is the user's own non-text content.

SMS OTP passes **only if paste or autofill works**. One-box-per-digit inputs fail if pasting the full code fills only the first box. Blocking paste fails.
- Salla login is a `salla-login-modal` (OTP, Salla-side).
- **Test:** On iOS Safari, request an OTP and confirm the "From Messages" autofill fills every digit. On macOS, paste a 4-digit code into the first box.
- Report: Salla-side if it fails.
- Source: accessible-authentication-minimum.html

## 2. Page structure, language and direction

- **R2.1** `<html lang>` matches the page language, and `dir` is set **in markup**, not CSS. A language tag doesn't set direction.
  - SC: 3.1.1, 1.3.2
  - **grep:** `grep -n "<html" src/views/layouts/master.twig`. Expect `lang="{{ language.code }}" dir="{{ theme.is_rtl ? 'rtl' : 'ltr' }}"` (master.twig:53, OK).
  - Source: qa-html-dir; language-of-page.html
- **R2.2** An opposite-language phrase gets `lang` (and `dir` if the direction differs). Examples: English product names, "UNIX", sizes like "XS" inside Arabic.
  - SC: 3.1.2 Language of Parts. Proper names and technical terms are excepted, so "UNIX" alone needs no `lang`.
  - **Test:** VO in Arabic reads an English product name with the English voice, or at least not as spelled-out Arabic letters. **UNVERIFIED** how far VO honours inline `lang` on iOS.
  - Source: language-of-parts.html
- **R2.3** Text inserted at runtime whose direction is unknown (product names, reviews, customer names, search terms) is wrapped in `<bdi>`, or gets `dir="auto"` on an existing wrapper. Text whose direction is known gets `<span dir="ltr">`. Wrap the opposite-direction phrase *tightly*.
  - SC: 1.3.2 Meaningful Sequence
  - **grep:** `grep -rn "<bdi\|dir=\"auto\"\|dir=\"ltr\"" src/views src/assets/js`
  - Source: inline-bidi-markup
- **R2.4** SKUs, order numbers, phone numbers, coupon codes and card digits inside Arabic sentences go in `<span dir="ltr">` (or `<bdi>`) so that neutral characters (`-`, `/`, `+`, `#`, `()`) keep their order.
  - "SKU: UX-2041/BLK" in an RTL line can render as "BLK/UX-2041" without isolation (inference from the article's neutral-character rules).
  - Use Unicode isolates (LRI, FSI, PDI) only where markup is impossible, such as `<title>`, attribute values and `aria-label`. Never use the embeddings (LRE, RLE, PDF).
  - SC: 1.3.2
  - **Test:** Render "طلب رقم #10234-A" and "+966 5x xxx xxxx" in AR; the digits must stay in order.
  - Source: inline-bidi-markup
- **R2.5** Form inputs that take free text get `dir="auto"`. Phone, email and code inputs get `dir="ltr"` with `text-align: end` in RTL, as a design choice.
  - SC: 1.3.2
  - Source: qa-html-dir
- **R2.6** Use logical CSS only (`margin-inline-start`, `inset-inline-end`, `text-align: start`). No `left` or `right`.
  - **grep:** `grep -rnE "(margin|padding|border)-(left|right)|[^-]left:|[^-]right:|text-align: *(left|right)" src/assets/styles --include=*.scss | grep -v unix-tokens`
  - Raed's Tailwind `ml-*`/`mr-*`/`space-x-*` need `rtl:` twins.
  - Source: qa-html-dir
- **R2.7** Directional icons (chevrons, arrows, "next") mirror in RTL. Non-directional icons (play, search, cart, heart, a clock) don't.
  - SC: 1.3.2, 1.3.3
  - **grep:** `grep -rn "icon-dir\|scaleX(-1)" src`
- **R2.8** Landmarks: one `header`, `nav` (each with a distinct `aria-label`), one `main id="main-content" tabindex="-1"` and one `footer`. The skip link is the first focusable element.
  - SC: 2.4.1, 1.3.1
  - **Test:** Tab once on any page and the skip link appears; Enter moves focus to `main`. VO rotor > Landmarks lists each landmark once.
  - Source: bypass-blocks.html; https://www.w3.org/WAI/ARIA/apg/patterns/landmarks/; https://web.dev/learn/accessibility/structure
- **R2.9** One `h1` per page with no skipped levels. Section headings come from merchant fields and must be real `h2`s, not styled `p`s. The hero title is `h1` only on the home page.
  - SC: 1.3.1, 2.4.6
  - **Test:** VO rotor > Headings. **grep:** `grep -rn "<h1" src/views | wc -l` and review each per template.
- **R2.10** `<title>` is unique and descriptive per page, in the page language.
  - SC: 2.4.2
  - Source: page-titled.html

## 3. Arabic typography and readability

- **R3.1** No `letter-spacing` on Arabic text. Arabic is cursive: moving joined letters apart "creates undesirable results" (ALReq §4.3.7.1). Stretching is done with kashida or tatweel, not tracking (§7.2.5, §7.3).
  - Tracking is allowed only under `html[lang="en"]` (DS §2.2).
  - **grep:** `grep -rn "letter-spacing" src/assets/styles | grep -v 'lang="en"\|letter-spacing: *0'`. Every hit must be inside an `html[lang="en"] &` block.
  - Source: https://www.w3.org/TR/alreq/#h_joining_and_spacing
- **R3.2** No synthetic italics on Arabic. ALReq doesn't address italics. The rule is a project typographic choice, because most Arabic fonts have no italic and the browser fakes an oblique (**UNVERIFIED** as a W3C requirement). Use weight or colour for emphasis.
  - **grep:** `grep -rn "font-style: *italic\|<em\|<i>" src/views src/assets/styles` (`<i class="sicon-…">` icon fonts are fine).
- **R3.3** Give Arabic body text a generous line-height, because Arabic ascenders, descenders and diacritics extend further than Latin (ALReq §7.4). ALReq gives no number; the project values are in DS §2.
  - SC: 1.4.12 Text Spacing requires that the content survive user overrides of line-height 1.5, paragraph spacing 2×, letter spacing 0.12em and word spacing 0.16em with no clipping. Fixed-height boxes with `overflow: hidden` fail.
  - **Test:** apply the text-spacing bookmarklet (https://www.html5accessibility.com/tests/tsbookmarklet.html, UNVERIFIED as W3C-endorsed) in AR, and check the 40px announcement bar, badges, buttons and the sticky ATC for clipping.
  - Source: text-spacing.html; alreq #h_baselines
- **R3.4** Don't use `text-transform: uppercase` on Arabic (it does nothing) or on screen-reader-relevant English. Uppercase is fine visually in EN; VO reads the DOM text, not the CSS case. **UNVERIFIED:** some screen readers spell out all-caps DOM text, so keep the DOM in sentence case and uppercase only with CSS.
- **R3.5** Reflow: at 320 CSS px (400% zoom) there is no 2-D scrolling, except data tables and the gallery.
  - SC: 1.4.10
  - **Test:** Chrome 1280px at 400% zoom in AR and EN, on the PDP, cart drawer and size chart. The size-chart table may scroll on its own; the page may not.
  - Source: reflow.html

## 4. Focus and keyboard (all components)

- **R4.1** Every control works with the keyboard. Use `<button>` for actions and `<a href>` for navigation. No `div` with a click handler.
  - SC: 2.1.1, 4.1.2
  - **grep:** `grep -rnE "<(div|span|li)[^>]*(onclick|data-.*click)" src/views` and `grep -rn "addEventListener('click'" src/assets/js` (check each target is a button or link).
  - Source: keyboard.html; https://web.dev/learn/accessibility/javascript
- **R4.2** No positive `tabindex`. Use `tabindex="-1"` only for programmatic targets (main, dialog headings, the step heading in the size finder).
  - SC: 2.4.3
  - **grep:** `grep -rnE 'tabindex="[1-9]' src` must be empty.
  - Source: https://web.dev/learn/accessibility/focus
- **R4.3** Focus is visible on every focusable element. `outline: none` is allowed only when a replacement ring exists (`::after`) or the element is a programmatic focus target.
  - The ring is ≥3:1 against adjacent colours. 1.4.11 covers this; 2.4.13 Focus Appearance is AAA, but web.dev recommends 3:1.
  - SC: 2.4.7, 1.4.11
  - **grep:** `grep -rn "outline: *none\|outline: *0" src/assets/styles`, then confirm each hit has a sibling `:focus-visible::after` ring or a reason. Known OK: `#main-content:focus` (unix-header.scss:54), the `.unix-sf__step` heading (unix-size-finder.scss:163), card `::after` rings (unix-blog.scss:234, unix-blog-pages.scss:165, unix-collections-grid.scss:166).
  - `reset.scss:47 a:focus{outline:none}` is overridden by `.theme-unix :focus-visible` (higher specificity), so check it still holds inside Salla light-DOM links.
  - Source: focus-visible.html; non-text-contrast.html
- **R4.4** Focus order follows the reading order, which is right to left in AR. Don't use CSS `order` or `flex-direction: row-reverse` to rearrange interactive items visually.
  - SC: 2.4.3, 1.3.2
  - **grep:** `grep -rn "row-reverse\|order:" src/assets/styles`
  - Source: focus-order.html
- **R4.5** No keyboard trap, except deliberate modal containment that Esc releases.
  - SC: 2.1.2
  - Source: no-keyboard-trap.html
- **R4.6** Arrow keys follow the reading direction. In RTL, ArrowLeft means *next*. APG doesn't state this; it is our rule and matches native RTL radio and tab behaviour (**UNVERIFIED** in APG).
  - **grep:** `grep -rn "ArrowLeft\|ArrowRight" src/assets/js`. Each handler must branch on `rtl` (as `unix-products-tabs.js:111` and `unix-gallery.js:127` do).
- **R4.7** No change of context on focus or input. A swatch or size choice can update the price or image, but must not navigate or submit. The colour links in `unix-colour-links.twig` are links, so navigation is expected.
  - SC: 3.2.1, 3.2.2
  - Source: on-input.html

## 5. Header, navigation and mega menu

- **R5.1** Site navigation uses the **disclosure** pattern (a `button[aria-expanded]` plus a list of links), *not* `role="menu"`/`menubar`. Menu roles promise application-style keyboard behaviour that site nav doesn't provide.
  - SC: 4.1.2
  - **grep:** `grep -rn 'role="menu\|role="menubar\|role="menuitem' src` should be empty, except a real menu button.
  - Source: APG disclosure-navigation example
- **R5.2** Esc closes an open dropdown and returns focus to its button. Moving focus out of the nav also closes it. APG calls Esc *required* for 1.4.13.
  - SC: 1.4.13, 2.1.1
  - **Test:** Kbd, open the desktop mega menu, Esc, and focus is back on the trigger.
  - Source: disclosure-navigation; content-on-hover-or-focus.html
- **R5.3** Hover-revealed content (mega menu, tooltips) must be dismissable (Esc), hoverable (the pointer can move into it) and persistent (it stays until dismissed).
  - SC: 1.4.13
  - **Test:** hover a menu item, move the pointer diagonally into the panel, and it stays open.
- **R5.4** The current page link has `aria-current="page"`.
  - SC: 1.3.1
  - **grep:** `grep -rn "aria-current" src/views src/assets/js`
- **R5.5** Icon-only header buttons (search, account, cart, menu, language) have names through `trans()`. The visible text is part of the name (for example "EN" means the name contains "EN").
  - SC: 4.1.2, 2.5.3 Label in Name
  - **Test:** VO, VO+Cmd+J through the header controls, in both languages.
  - Source: label-in-name.html
- **R5.6** The cart count is part of the cart button's name ("السلة، 3 منتجات") or a status region, not a bare "3".
  - SC: 4.1.3, 1.3.1
  - Source: status-messages.html
- **R5.7** Mobile menu drawer: see §6.

## 6. Dialogs and drawers (cart drawer, mobile menu, filters, search, size chart, size finder, gallery lightbox)

APG Dialog (Modal):
- **R6.1** The container is `role="dialog"` with `aria-modal="true"` and `aria-labelledby` pointing to a visible title. Use `aria-modal` only when the outside content really is inert *and* visually obscured.
  - SC: 4.1.2, 1.3.1
  - **grep:** `grep -rn 'role="dialog"' src/views`. Each needs `aria-labelledby` or `aria-label` (cart drawer `unix-cart-drawer.twig:26`, mobile menu `header.twig:175`, filters `product/index.twig:180`).
- **R6.2** On open, focus moves inside the dialog:
  - by default to the first focusable element;
  - to a `tabindex="-1"` heading for long or structured content (cart line list, size chart);
  - to the least destructive button when the action can't be undone ("remove item?").
  - SC: 2.4.3
- **R6.3** Tab and Shift+Tab wrap inside the dialog, and Esc closes it.
  - SC: 2.1.1, 2.1.2
  - **Test:** Kbd, open the cart drawer, Tab 30 times; focus never reaches the page. Then Shift+Tab from the first element wraps to the last.
- **R6.4** On close, focus returns to the trigger. If the trigger is gone (for example the sticky ATC was hidden), it goes to a logical next element (`focusTarget` in `unix-drawer.js:99–117`).
  - SC: 2.4.3
- **R6.5** The background is inert. Prefer the native `inert` attribute (we set it on `.app-inner`). The dialog must not sit inside an `aria-hidden` or inert subtree. Drawers are siblings of `.app-inner` (unix-drawer.js:22).
  - **Test:** With the drawer open, VO+Right past the last drawer item must not reach page content. On iOS, a three-finger swipe should not leave the drawer.
- **R6.6** There is a visible close button (≥24px AA, 44px project) with a translated name.
- **R6.7** Native `<dialog>` with `showModal()` is acceptable and gives inertness for free; mixing it with a custom trap is not.
- **R6.8** Third-party modals (`salla-login-modal`, `salla-quick-buy`) are Salla-side. When opening one from a drawer, close the drawer with `returnFocus:false` so two traps don't fight (unix-drawer.js:101).

Source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/; https://web.dev/learn/accessibility/javascript

## 7. Product gallery and carousels

- **R7.1** Every product image has meaningful `alt`: the merchant alt, falling back to the product name plus the image index ("ليقنز UNIX أسود – صورة 2 من 5"). Decorative duplicates, such as the hover second image, get `alt=""` and `aria-hidden`.
  - SC: 1.1.1
  - **grep:** `grep -rn "<img" src/views src/assets/js | grep -v 'alt='` must be empty.
  - Source: non-text-content.html; https://web.dev/learn/accessibility/images
- **R7.2** A carousel container is `region` or `group` with `aria-roledescription="carousel"` and a label *without* the word "carousel". Slides are `group` with `aria-roledescription="slide"`.
  - Name slides descriptively. "3 of 10" is only a fallback, because `group` doesn't support `aria-setsize` or `aria-posinset`.
  - SC: 1.3.1, 4.1.2
  - Source: https://www.w3.org/WAI/ARIA/apg/patterns/carousel/
- **R7.3** Prev and next are real buttons, so swipe is never the only way.
  - Thumbnails are buttons with `aria-current="true"` on the active one (`unix-gallery.twig:129`), or a tabs pattern ("tabbed carousel").
  - SC: 2.5.1, 2.5.7, 2.1.1
- **R7.4** Auto-rotating carousels:
  - a stop/start button that is first in the carousel's Tab order;
  - rotation stops on keyboard focus and on hover, and resumes only when the user asks;
  - `aria-live="off"` on the slide wrapper while rotating and `polite` while stopped.
  - Our product carousels don't auto-rotate; keep it that way.
  - SC: 2.2.2
- **R7.5** Lightbox and zoom: the zoom toggle is a `button[aria-pressed]` (`unix-gallery.twig:146`). The counter is a polite live region (`:143`). Arrow keys are direction-aware. Esc closes the lightbox and returns focus to the image that opened it.
- **R7.6** Pinch-zoom must stay possible. No `user-scalable=no` or `maximum-scale=1`.
  - SC: 1.4.4
  - **grep:** `grep -rn "user-scalable\|maximum-scale" src` must be empty.
- **R7.7** Horizontal scroll strips (collections grid, product tabs) use native `overflow` and `scroll-snap`, which is exempt from 2.5.7. If JS takes over dragging, buttons are required.

## 8. Tabs (home products tabs)

- **R8.1**
  - `role="tablist"` with a label;
  - `role="tab"` with `aria-selected` and `aria-controls`;
  - `role="tabpanel"` with `aria-labelledby`;
  - `tabindex="0"` on the panel if it has no focusable content.
  - Implemented at `unix-products-tabs.twig:136–166`.
  - SC: 4.1.2, 1.3.1
- **R8.2** Keyboard:
  - Tab lands on the *active* tab only (roving `tabindex="-1"` on the others);
  - Left/Right move between tabs and wrap (mirrored in RTL);
  - Home/End go to the first and last tab;
  - Tab again moves into the panel.
  - Use manual activation (Enter/Space) when panels load over the network; we do.
  - **Test:** Kbd in AR: ArrowLeft goes to the *next* tab visually to the left.
  - Source: https://www.w3.org/WAI/ARIA/apg/patterns/tabs/

## 9. Accordion and disclosure (FAQ, PDP details, filter groups, "add note")

- **R9.1** The trigger is a `<button>` inside a heading (accordion), with `aria-expanded` kept in sync and optional `aria-controls`. Enter and Space toggle. Native `<details>/<summary>` is acceptable and preferred where styling allows.
  - SC: 4.1.2
  - **grep:** `grep -rn "btn--collapse\|data-show=" src/views` and confirm each trigger gets `aria-expanded` from JS.
  - Sources: https://www.w3.org/WAI/ARIA/apg/patterns/accordion/; https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/
- **R9.2** Collapsed content is hidden from AT (`hidden`, `display:none` or `inert`), not just `max-height:0` while staying focusable.
  - SC: 2.4.3, 1.3.1
  - **Test:** Kbd, Tab past a closed FAQ item; focus must not enter its hidden links.

## 10. Variant selection: size and colour swatches, sold-out state

- **R10.1** A single-choice option group is a **radio group**.
  - Prefer native `<fieldset><legend>المقاس</legend><input type="radio">…` with styled labels.
  - Custom: `role="radiogroup"` with a label, `role="radio"` and `aria-checked`. Arrows move *and* select. Tab enters on the checked radio.
  - Use `listbox` only for a list-style picker that isn't styled as radios. Don't use `aria-pressed` buttons for mutually exclusive choices.
  - SC: 1.3.1, 4.1.2
  - Sources: https://www.w3.org/WAI/ARIA/apg/patterns/radio/; https://www.w3.org/WAI/ARIA/apg/patterns/listbox/
  - Salla's `salla-product-options` renders these (Salla-side). Audit what reaches the a11y tree: VO rotor > Form Controls should show "XS, radio button, 1 of 6".
- **R10.2** A colour swatch's name is the colour name, not the hex value or an empty button. Colour alone never carries meaning: the selected state also shows as a ring or border plus the visible chosen-value text ("اللون: أسود").
  - SC: 1.1.1, 1.4.1
  - Source: use-of-color.html
- **R10.3** The selected swatch ring and swatch border reach 3:1 against the adjacent colours. Check a white or sand swatch on the `--c-bg` cream.
  - SC: 1.4.11
- **R10.4** A sold-out size is announced, not only shown struck-through or greyed. Use the name "M – نفدت الكمية", or `aria-describedby`.
  - Disabled-looking text is exempt from 1.4.3 only when the control is truly disabled. If it can still be chosen (for "notify me"), it needs 4.5:1.
  - SC: 1.4.1, 1.3.1, 1.4.3
  - **Test:** VO on a sold-out size reads the state in AR and EN.
- **R10.5** A product-level out-of-stock message is `role="status"` (`product/single.twig:232`). The add button changes its *name* to «نفدت الكمية» or the notify label, and isn't just greyed.
- **R10.6** The colour links between sibling products (`unix-colour-links.twig`) are links with `aria-current="page"` on the current one, not radios. That is correct because they navigate.
- **R10.7** The size guide and Size Finder triggers are buttons that open dialogs (§6). The Size Finder result goes in a polite live region or gets focus on its heading. The step heading takes focus via `tabindex="-1"`.
  - SC: 4.1.3

## 12. Add to cart, cart drawer, toasts and live regions

- **R12.1** Add-to-cart success, the cart count change, filter result counts, the free-shipping progress and the delivery estimate are **status messages** in a live region that exists *before* the text changes.
  - Set `textContent`; don't inject a new region with its text in one go. If you must create the region, defer the first write (`setTimeout`).
  - SC: 4.1.3
  - **grep:** `grep -rn 'role="status"\|aria-live' src/views src/assets/js`
  - Known regions: `unix-cart-drawer.twig:98`, `product/index.twig:144`, `unix-free-shipping.twig:49`, `unix-delivery-estimate.twig:83`, `unix-size-charts.twig:42`.
  - Source: MDN Live regions; status-messages.html
- **R12.2** Use `polite` (`role="status"`) by default. Use `role="alert"` only for blocking errors ("the quantity isn't available"). Never set `role="alert"` together with `aria-live="assertive"`: iOS VO speaks it twice.
- **R12.3** Announce the whole meaningful string ("أُضيف إلى السلة: ليقنز UNIX، المقاس M. في السلة 3 منتجات"), not "3". Use `aria-atomic="true"` when a partial update would read as a fragment.
- **R12.4** If the cart drawer opens after add-to-cart, focus moves into it (§6) and the drawer title is announced. Then no extra live message is needed: focus-moving changes are outside 4.1.3. Don't do both, or users hear it twice.
- **R12.5** A toast that disappears on its own: under 2.2.1 Timing Adjustable, the essential info must also live somewhere persistent (cart count, drawer). Toasts must not take focus and must not cover the focused element (2.4.11).
  - **grep:** `src/assets/js/partials/add-product-toast.js` (setTimeout at :118).
- **R12.6** Quantity steppers have named +/− buttons ("زيادة الكمية"), an input with a label, and an announced result. Remove buttons name the product ("حذف ليقنز UNIX").
  - SC: 2.4.6, 4.1.2
- **R12.7** Busy state: the add button exposes busy (`aria-busy`, or disabled with a text change) and doesn't steal focus on completion. `salla-add-product-button` is Salla-side; check the theme label passes through (LESSONS #3).
- **R12.8** The free-shipping progress bar is decorative next to its text message, or `role="progressbar"` with `aria-valuenow/min/max` *and* a text value. Don't use both.

  - SC: 4.1.3
- **R13.3** The search input has a label (it can be visually hidden), `type="search"`, and `enterkeyhint="search"` for a better mobile keyboard (best practice).

## 15. Media: hero video, video tiles, motion

- **R15.1** Autoplaying video that runs more than 5s next to other content needs a visible pause/stop control. That applies even to muted video, because the rule is about motion. Pausing on hover or focus alone is **not** a mechanism.
  - SC: 2.2.2
  - Our hero (`unix-hero.twig:147`, JS `unix-hero.js:7–52`) and video tiles (`unix-video-tiles.twig:100`) have 44px toggle buttons. Good.
  - Source: pause-stop-hide.html
- **R15.2** Toggle naming: either a fixed name plus `aria-pressed` ("إيقاف الفيديو", pressed while paused), *or* a name that changes with no `aria-pressed`. Never both. Our hero uses the fixed name plus `aria-pressed` (OK).
  - SC: 4.1.2
  - Source: APG button pattern (https://www.w3.org/WAI/ARIA/apg/patterns/button/)
- **R15.3** `prefers-reduced-motion: reduce` means no autoplay (the poster stays), no parallax or slide transitions, and an instant announcement swap.

  - Source: animation-from-interactions.html; https://web.dev/learn/accessibility/motion
- **R15.4** Videos with speech or meaningful content have captions (1.2.2) and a text alternative or audio description (1.2.3/1.2.5). Silent mood loops are decorative: `aria-hidden="true"` on the `<video>`, with the information carried by the text beside it.
  - Source: https://web.dev/learn/accessibility/video-audio
- **R15.5** No audio autoplays for more than 3s without a control.
  - SC: 1.4.2
  - **grep:** `grep -rn "<video" src/views | grep -v muted`

## 16. Contrast (tokens, images, states)

- **R16.1** Text is 4.5:1. Large text (≥24px, or ≥18.66px bold) is 3:1. UI component boundaries, focus rings, icons and swatch rings are 3:1. Logos and incidental text are exempt; disabled controls are exempt only when actually disabled.
  - SC: 1.4.3, 1.4.11
  - **Test:** take token pairs from `unix-tokens.scss` and check them at https://webaim.org/resources/contrastchecker/ (third-party tool; the WCAG formula is in the Understanding doc).
  - Source: contrast-minimum.html; non-text-contrast.html; https://web.dev/learn/accessibility/color-contrast
- **R16.2** Text on an image or video is measured against the *worst* area behind the glyphs. Guarantee it with a scrim or gradient token, or a solid backing. While a video loads, the fallback colour behind the text must also pass (DS: the hero falls back to sand with ink text, `unix-hero.twig:21,58`).
  - **Test:** screenshot the hero at 375/768/1280 in AR (text aligned to the right edge) and EN, then sample the lightest pixel under the text.
  - **UNVERIFIED:** WCAG gives no formal method for gradients. Use the worst-case pixel.
- **R16.3** Opacity-muted text (`opacity: var(--o-muted)` on inverse text, as in `unix-collection-overlay.scss`) must be recomputed as the blended colour against the real background.
- **R16.4** Muted states (placeholder text, struck old price, sold-out size) still meet 4.5:1 when the user needs to read them. Placeholders are text, so they count.
- **R16.5** Windows High Contrast / forced-colors: borders and focus rings use `outline`/`border`, not just `box-shadow` or `background`, which forced colors drops. **Test:** Chrome DevTools > Rendering > emulate `forced-colors: active`.
  - UNVERIFIED as a WCAG requirement; it supports 1.4.11.

## 17. Links, buttons and names (product cards and general)

- **R17.1** A link's purpose comes from its text or context. A card's image link and title link go to the same URL: make one of them `tabindex="-1" aria-hidden="true"`, or use a single overlay link, so there aren't two tab stops with different names.
  - SC: 2.4.4
  - **grep:** `src/assets/js/partials/product-card.js:271,285`
  - Source: link-purpose-in-context.html
- **R17.2** The card link name is the **product name**, not merchant image alt text (which may be "IMG_2041" or "صورة").
  - SC: 2.4.4, 2.5.3
- **R17.3** The wishlist heart has a fixed name ("أضيفي إلى المفضلة: <product>") plus `aria-pressed` on the inner focusable `<button>` (LESSONS #6). The state lives in `aria-pressed` only.
  - SC: 4.1.2
- **R17.4** "Read more" or "تسوقي الآن" repeated across cards: add the item name in visually hidden text, or use `aria-labelledby` combining the link and title. 2.4.4 is the minimum.
- **R17.5** Links that open a new tab say so (an icon with text such as "(تفتح في نافذة جديدة)"). Best practice, G201.
- **R17.6** Never put interactive content inside a link (button in `<a>`), and never put a heading-less "card" link around buttons.
  - SC: 4.1.2

## 18. Announcement bar and other auto-updating UI

- **R18.1** Rotating messages are "moving/auto-updating" content. If they run more than 5s alongside other content, they need a pause/stop/hide mechanism. Per the Understanding doc, stopping only while focused or hovered "would not be considered a mechanism".
  - SC: 2.2.2
  - **Test:** Is there a visible pause control, or a setting that disables rotation?
  - Source: pause-stop-hide.html
- **R18.2** No `aria-live` on rotating content (correct in our bar). Every message stays in the DOM as a list, so screen reader users can read all of them.

## 19. Salla web components (shadow DOM)

- **R19.1** The theme controls: labels passed in (`trans()` feminine), slots, host styling, CSS parts and variables, and contrast of the colours we set. Audit those as theme issues.
- **R19.2** Inside shadow DOM, missing names, roles and traps are **Salla-side**. Workarounds:
  - pass `aria-label` or a slot text;

- **R19.3** `aria-labelledby`/`aria-describedby` IDREFs **don't cross shadow boundaries**. A light-DOM label can't name a shadow input by ID. Use the component's own label prop.
  - Source: DOM/ARIA spec behaviour. **UNVERIFIED** against a specific Salla component; check in the a11y tree.

## 20. Common failures in themes (check these first)

1. `outline: none` with no replacement ring, often in reset files or on cards that "use the image hover as focus". (2.4.7)
2. Fixed header or sticky ATC hides the focused element when tabbing backwards; no `scroll-padding`. (2.4.11)
3. Drawers where focus stays on the page behind, Esc does nothing, or focus is dropped to `<body>` on close. (2.4.3, 2.1.2)
4. A live region injected together with its text, so nothing is announced. Or `role="alert"` plus `aria-live="assertive"`, which iOS VO speaks twice. (4.1.3)
5. Swatches as `div`s, or buttons with no name ("button" ×6) and colour-only selection. (4.1.2, 1.4.1)
6. Sold-out sizes shown only with a strike-through or light grey under 4.5:1. (1.4.1, 1.4.3)
7. Hero text on photos with no scrim, passing on one image and failing when the merchant changes it. (1.4.3)
8. Autoplay video or rotating banner with no pause control, or "pause on hover" only. (2.2.2)
9. Carousels that are swipe-only, or with arrows under 24px. (2.5.1, 2.5.7, 2.5.8)
10. Duplicate card links (image and title), plus a heart button named "like". (2.4.4, 4.1.2)
11. Disclosure toggles that change a class but never `aria-expanded`. (4.1.2)
12. `role="menu"` on the site nav, which makes screen readers expect arrow-key menu behaviour. (4.1.2)
13. Placeholder-only inputs, and errors in red text with no `aria-describedby`/`aria-invalid`. (3.3.1, 3.3.2)
14. OTP boxes that block paste, or split boxes that ignore a pasted code. (3.3.8)
15. `letter-spacing` or `uppercase` utilities applied globally, breaking Arabic joins; synthetic italics on Arabic. (ALReq)
16. `left`/`right`, `ml-`/`mr-`, and un-mirrored chevrons; arrow keys that move the wrong way in RTL. (1.3.2)
17. Mixed-direction strings (SKU, phone, order #, English names) reordered by bidi because they aren't isolated. (1.3.2)
18. `maximum-scale=1` in the viewport meta. (1.4.4)
19. Fixed-height text boxes that clip at 1.5 line-height or 200% zoom. (1.4.12, 1.4.4)
20. Help or contact link moved to a different DOM position on one template. (3.2.6)
